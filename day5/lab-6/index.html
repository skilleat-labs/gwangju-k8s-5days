    실습 6. 고장 난 미니 블로그 고치기¶

    이번 실습에서 할 것

    • 세 군데가 고장 난 미니 블로그를 올립니다.
    • get, describe, logs, events 순서로 증상에서 원인으로 좁혀 갑니다.
    • 전부 지우지 않고 고장 난 리소스만 고쳐서 글 등록까지 되게 만듭니다.
    • 찾은 과정을 진단 기록(증상, 근거, 수정, 재확인)으로 남깁니다.
    • webapp을 켜 둔 채로, broken 블로그가 자기 백엔드만 쓰는지 확인합니다.

    소요 시간 약 12분, 교안 DAY 5 섹션 6

    준비¶

    작업 폴더로 이동합니다.

    cd $HOME\k8s-labs\day5

    cd ~/k8s-labs/day5

    고장 난 블로그 파일을 내려받아 작업 폴더에 넣습니다. 이 파일은 broken 네임스페이스에 Namespace, PVC, backend, frontend를 모두 만듭니다. Gateway는 없고 port-forward로 엽니다.

    broken의 frontend는 v4-kb5

    broken의 frontend 이미지는 skilleat/frontend:v4-kb5입니다. 이 태그는 자기 네임스페이스의 backend-service를 짧은 이름으로 부릅니다. 그래서 실습 5의 webapp이 살아 있어도 broken의 고장을 대신 받아 주지 않습니다. backend는 실습 5와 같은 v3-kb5를 쓰도록 되어 있습니다(지금은 고장 나 있습니다).

    실습 5의 webapp은 지우지 않고 그대로 둡니다.

    broken-blog.yaml 내려받기

    YAML을 눈으로 훑어서 찾지 마세요

    실무 YAML은 수백 줄이라 눈으로 찾을 수 없습니다. 반드시 아래 루틴대로 증상부터 보고, 증상이 가리키는 줄을 고칩니다. 파일 내용은 답을 다 찾은 뒤 맨 아래에서 볼 수 있습니다.

    장애 찾기 루틴: 넓게 보고 좁혀 간다¶

    순서 명령 보는 곳
    1. get kubectl get pods,pvc -n broken STATUS, READY로 어디가 이상한지
    2. describe kubectl describe pod -n broken -l app=backend 맨 아래 Events에 쿠버네티스가 본 원인
    3. logs kubectl logs -n broken -l app=frontend 앱이 남긴 오류. 재시작됐으면 --previous
    4. events kubectl get events -n broken --sort-by=.lastTimestamp 네임스페이스 전체를 시간순으로

    연결 문제(Pod는 Running인데 기능이 안 됨)는 events에 안 나옵니다. 그때는 Service 다음에 EndpointSlice를 봅니다 (3일차 실습 4).

    STEP 30. 고장 난 블로그 올리기¶

    kubectl apply -f broken-blog.yaml

    namespace/broken created
persistentvolumeclaim/blog-pvc created
deployment.apps/backend created
service/backend-service created
deployment.apps/frontend created
service/frontend-service created

    모두 created로 성공합니다. apply가 성공했다고 앱이 동작하는 것은 아닙니다.

    새 터미널을 열어 broken의 화면을 엽니다. 실습 5의 8080, 8888과 겹치지 않게 8081을 씁니다. 이 터미널은 STEP 33까지 켜 둡니다.

    kubectl port-forward -n broken svc/frontend-service 8081:80

    브라우저에서 http://localhost:8081 을 열고 글을 하나 써 봅니다. 화면은 뜨지만 글 쓰기는 실패해야 정상입니다. backend가 고장 났고, frontend는 webapp의 백엔드로 새지 않기 때문입니다. 글이 써진다면 강사에게 알려 주세요.

    원래 터미널로 돌아와 STEP 31을 합니다.

    STEP 31. 루틴대로 좁혀 가기¶

    아래 명령을 순서대로 쓰면서 증상을 하나씩 찾습니다.

    kubectl get pods,pvc -n broken

    kubectl describe pod -n broken -l app=backend

    kubectl get events -n broken --sort-by=.lastTimestamp

    kubectl get endpointslices -n broken

    고장은 한 번에 하나씩 드러납니다. 하나를 찾으면 VS Code에서 broken-blog.yaml의 그 부분만 고치고 STEP 32의 해당 방법으로 반영한 뒤, STEP 31을 처음부터 다시 합니다.

    진단 기록¶

    고장 하나를 찾을 때마다 한 줄씩 채워 채팅에 올립니다. 첫 줄은 예시입니다.

    증상 근거 (명령과 본 칸) 수정 재확인
    예시 PVC, backend Pod가 Pending describe pvc의 Events PVC만 지우고 다시 apply PVC Bound, Pod가 다음 단계로
    2
    3

    재확인을 빼먹지 않습니다. 고쳤다고 생각했는데 다음 고장이 드러난 것을 놓치기 쉽습니다.

    힌트 1: 첫 번째 고장

    get pods,pvc에서 backend Pod와 PVC가 둘 다 Pending입니다. Pod는 PVC를 기다리는 중이니 PVC 쪽을 describe합니다.

    kubectl describe pvc blog-pvc -n broken

    Events에 나오는 StorageClass 이름이 클러스터에 실제로 있는지 봅니다.

    kubectl get storageclass
    힌트 2: 두 번째 고장

    PVC가 Bound가 되면 backend Pod가 이번에는 ErrImagePull 또는 ImagePullBackOff입니다. describe의 Events에 찍힌 이미지 이름과 태그를 실습 5에서 쓴 이미지(skilleat/backend:v3-kb5)와 한 글자씩 비교합니다.

    힌트 3: 세 번째 고장

    Pod가 모두 Running인데 화면에서 글 등록만 실패합니다. Service 뒤에 Pod가 붙어 있는지 봅니다.

    kubectl get endpointslices -n broken -l kubernetes.io/service-name=backend-service

    ENDPOINTS가 비어 있으면 Service의 SELECTOR와 Pod의 LABELS를 비교합니다.

    kubectl get svc backend-service -n broken -o wide

    kubectl get pods -n broken --show-labels

    frontend 로그에도 백엔드에 연결하지 못한 흔적이 남습니다.

    kubectl logs -n broken -l app=frontend

    STEP 32. 고친 리소스만 다시¶

    전부 지우고 다시 만들지 않습니다. 고장 난 리소스만 고칩니다. 고장마다 방법이 다릅니다.

    image, selector 고장: 파일 고친 뒤 apply만¶

    이미지 태그 오타(Deployment)와 selector 오타(Service)는 VS Code에서 파일의 그 줄만 고친 뒤 아래 명령 하나만 실행합니다. PVC는 지우지 않습니다.

    kubectl apply -f broken-blog.yaml

    kubectl apply -f는 파일 전체를 다시 보내도 바뀐 리소스만 갱신하고, 나머지는 unchanged로 둡니다. image를 고치면 새 ReplicaSet이 새 Pod를 만들고, selector를 고치면 Pod는 그대로이고 연결만 바로 생깁니다.

    StorageClass 고장일 때만: Pending PVC를 지우고 다시¶

    storageClassName은 만든 뒤 바꿀 수 없어서 apply만 하면 거부됩니다. 이 방법은 한 번도 Bound된 적이 없어 데이터가 없는 PVC에만 씁니다. kubectl get pvc -n broken에서 STATUS가 Pending인지 먼저 확인합니다.

    파일의 storageClassName 줄을 고친 뒤 실행합니다.

    kubectl delete pvc blog-pvc -n broken

    kubectl apply -f broken-blog.yaml


    namespace/broken unchanged
persistentvolumeclaim/blog-pvc created
deployment.apps/backend unchanged
service/backend-service unchanged
deployment.apps/frontend unchanged
service/frontend-service unchanged
    출력은 예시입니다. 이름, IP, 시간은 사람마다 다릅니다.

    Bound된 PVC는 지우지 않습니다

    PVC 삭제는 데이터가 없는 Pending PVC일 때만 쓰는 방법입니다. image나 selector를 고칠 때 이 명령을 따라 치지 않습니다. 글이 들어 있는 Bound PVC를 지우면 reclaimPolicy에 따라 데이터가 함께 지워질 수 있고, 사용 중인 PVC는 보호 장치 때문에 Terminating에 머뭅니다. kubectl delete -f broken-blog.yaml로 Namespace까지 통째로 지우는 것도 처음부터 다시 할 때만 씁니다.

    STEP 33. 다 고친 뒤 확인¶

    세 군데를 다 고쳤으면 backend 교체가 끝날 때까지 기다립니다.

    kubectl rollout status deployment/backend -n broken --timeout=180s

    deployment "backend" successfully rolled out

    STEP 30에서 켜 둔 8081 port-forward 화면(http://localhost:8081)에서 글을 하나 씁니다. 이번에는 목록에 나옵니다. 8081 터미널이 끊겼으면 STEP 30의 port-forward를 다시 실행합니다.

    마지막으로 실습 5의 webapp 블로그(http://localhost:8888)를 새로고침합니다. 방금 broken에 쓴 글은 webapp에는 없습니다. 두 블로그가 각자 자기 네임스페이스의 백엔드와 PVC를 쓴다는 증거입니다. 8888이 끊겼으면 실습 5 STEP 24의 port-forward를 다시 실행합니다.

    확인한 뒤 port-forward 터미널에서 Ctrl + C로 멈춥니다.

    성공하면¶

    • Pod Running, PVC Bound
    • EndpointSlice에 주소가 있다
    • STEP 30: 고치기 전 8081 글 쓰기 실패
    • STEP 33: 8081 글 등록 성공, 그 글이 8888(webapp)에는 없음
    • 진단 기록 세 줄

    정답¶

    다 찾은 뒤에 열어 봅니다.

    정답 1: PVC Pending (StorageClass 없음)

    증상: get pods,pvc에서 PVC와 backend Pod가 Pending.

    NAME                             STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   AGE
persistentvolumeclaim/blog-pvc   Pending                                      fast-ssd       20s

    describe pvc의 Events:

    Warning  ProvisioningFailed  ...  storageclass.storage.k8s.io "fast-ssd" not found
    출력은 예시입니다. 이름, IP, 시간은 사람마다 다릅니다.

    원인: 클러스터에 없는 fast-ssd StorageClass를 요청했습니다. kubectl get storageclass에는 hostpath만 있습니다.

    고치기: PVC의 storageClassName: fast-ssd 줄을 지웁니다 (기본 StorageClass 사용). 또는 storageClassName: hostpath로 바꿉니다. 이 PVC는 Pending이라 데이터가 없으므로 kubectl delete pvc blog-pvc -n broken 후 kubectl apply -f broken-blog.yaml. 이 PVC 삭제는 이 고장에만 씁니다.

    정답 2: ImagePullBackOff (이미지 태그 오타)

    증상: backend Pod가 ErrImagePull → ImagePullBackOff.

    Warning  Failed   ...  Failed to pull image "skilleat/backend:v3-kb55": ... not found
Warning  Failed   ...  Error: ErrImagePull
Normal   BackOff  ...  Back-off pulling image "skilleat/backend:v3-kb55"
    출력은 예시입니다. 실제로는 failed to resolve reference 같은 문구가 길게 붙습니다.

    원인: 태그 v3-kb55가 Docker Hub에 없습니다.

    고치기: image: skilleat/backend:v3-kb5로 바로잡고 kubectl apply -f broken-blog.yaml만 합니다. Deployment만 바뀝니다. PVC는 지우지 않습니다.

    정답 3: 빈 EndpointSlice (Service selector 오타)

    증상: Pod는 모두 Running, 화면은 뜨는데 글 등록만 실패. EndpointSlice가 비어 있습니다.

    NAME                    ADDRESSTYPE   PORTS     ENDPOINTS   AGE
backend-service-8fz2q   IPv4          <unset>   <unset>     2m


    NAME              TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)    AGE   SELECTOR
backend-service   ClusterIP   10.96.77.10    <none>        5000/TCP   2m    app=backnd
    출력은 예시입니다. 이름, IP, 시간은 사람마다 다릅니다.

    원인: Service의 selector가 app: backnd, Pod 라벨은 app=backend입니다. 고른 Pod가 없어서 Service 뒤가 비었습니다. Service는 오류 이벤트를 남기지 않아서 events만 봐서는 못 찾습니다.

    고치기: selector: {app: backend}로 바로잡고 kubectl apply -f broken-blog.yaml만 합니다. Service만 바뀝니다. PVC는 지우지 않습니다.

    고장 난 파일 전체 보기 (broken-blog.yaml)
    broken-blog.yaml
    # 고장 난 미니 블로그 (DAY 5 실습 6)
# 세 군데가 틀렸다. YAML 을 눈으로 훑지 말고, get, describe, logs, events 순서로 증상부터 찾는다.
apiVersion: v1
kind: Namespace
metadata:
  name: broken
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: blog-pvc
  namespace: broken
spec:
  storageClassName: fast-ssd
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  namespace: broken
spec:
  replicas: 1
  # 글을 파일 하나에 쓰는 앱 + ReadWriteOnce PVC: 옛 Pod 를 먼저 내리고 새 Pod 를 띄운다.
  # 업데이트 중 잠깐 API 가 멈추지만, 두 Pod 가 같은 파일에 동시에 쓰는 일이 없다.
  strategy:
    type: Recreate   # 파일 하나에 쓰는 백엔드: 새 Pod 전에 옛 Pod 를 먼저 끈다
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
      - name: backend
        image: skilleat/backend:v3-kb55
        ports:
        - containerPort: 5000
        volumeMounts:
        - name: data
          mountPath: /app/data
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: blog-pvc
---
apiVersion: v1
kind: Service
metadata:
  name: backend-service
  namespace: broken
spec:
  selector: {app: backnd}
  ports:
  - port: 5000
    targetPort: 5000
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: broken
spec:
  replicas: 1
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      containers:
      - name: frontend
        image: skilleat/frontend:v4-kb5   # 같은 네임스페이스의 backend-service 를 부르는 태그
        ports:
        - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: frontend-service
  namespace: broken
spec:
  selector:
    app: frontend
  ports:
  - port: 80
    targetPort: 80

    왜 한 번에 하나씩 드러나나

    PVC가 Pending이면 Pod가 노드에 배치되지 않아 이미지를 받으려는 시도조차 없습니다. 그래서 이미지 오류가 아직 안 보입니다. 이미지를 고쳐 Pod가 Running이 되어야 비로소 라벨 오류가 글 등록 실패로 드러납니다. 실무 장애도 이렇게 겹겹이 숨어 있습니다.

    막히면¶

    error: no objects passed to apply / the path \"broken-blog.yaml\" does not exist

    작업 폴더에 파일이 없습니다. ls로 확인하고 cd로 작업 폴더로 이동합니다. 브라우저가 broken-blog (1).yaml처럼 이름을 바꿔 저장했을 수 있습니다.

    The PersistentVolumeClaim \"blog-pvc\" is invalid: spec: Forbidden: spec is immutable after creation

    storageClassName을 고치고 apply만 다시 했습니다. PVC가 Pending(한 번도 Bound 안 됨)인지 확인한 뒤, STEP 32의 StorageClass 방법대로 kubectl delete pvc blog-pvc -n broken 후 apply합니다. Bound된 PVC라면 지우지 말고 강사에게 알려 주세요.

    PVC가 Terminating에 머물러 지워지지 않음

    그 PVC를 쓰는 Pod가 노드에 배치돼 있으면 보호 장치 때문에 Pod가 없어질 때까지 기다립니다. kubectl delete pod -n broken -l app=backend로 backend Pod도 지우면 PVC가 지워지고, Deployment가 새 Pod를 만듭니다.

    Error from server (Forbidden): ... namespace broken because it is being terminated

    delete -f로 네임스페이스를 지운 직후입니다. kubectl get ns broken에 아무것도 안 나올 때까지 몇 초 기다린 뒤 다시 apply합니다. 이 실습에서는 네임스페이스를 지울 필요가 없습니다.

    kubectl logs: container \"backend\" in pod ... is waiting to start

    컨테이너가 아직 시작되지 않았습니다 (Pending이거나 이미지를 못 받음). 로그가 없는 단계이니 describe의 Events를 봅니다.

    Unable to listen on port 8081

    8081을 다른 프로그램이 쓰고 있습니다. 8082:80처럼 앞 숫자를 바꾸고 그 포트로 엽니다.

    정리¶

    kubectl delete ns broken webapp

    실습 5의 webapp과 이 실습의 broken이 함께 지워집니다. 과정 전체를 정리하려면 아래 과정 마무리를 따라 합니다.

    과정 마무리¶

    5일 동안 수고하셨습니다. 1일차에 docker run으로 손수 띄우던 미니 블로그를, 오늘 YAML 두 장으로 쿠버네티스에 맡기고, 지키고, 고쳤습니다. 막히면 get, describe, logs, events부터 보세요.

    일차 한 일
    1일차 컨테이너 컨테이너는 격리된 프로세스. 미니 블로그를 도커로 띄우고 한계 5가지를 겪었다
    2일차 구조와 배포 클러스터 구조, Pod, Deployment. 자가복구, 확장, 롤링 업데이트
    3일차 서비스 Service, DNS, EndpointSlice, Gateway API. 변하지 않는 주소와 입구
    4일차 설정과 데이터 ConfigMap, Secret, probe, limits, PVC. 이미지 밖으로 빼고 지킨다
    5일차 보안과 종합 root 금지, RBAC, NetworkPolicy. 미니 블로그를 YAML로 옮기고 고쳤다

    보안은 여러 겹¶

    층 이 과정에서 한 것 다음 단계
    신원 ServiceAccount, kubeconfig 인증서 회사 계정 연동 (OIDC)
    권한 RBAC 최소 권한, 토큰 자동 마운트 끄기 정기 권한 점검, 감사 로그
    실행 securityContext, PSA restricted 정책 엔진 (Kyverno, OPA Gatekeeper)
    네트워크 NetworkPolicy 기본 차단 후 허용 서비스 메시 mTLS
    비밀 Secret으로 이미지 밖에 보관 etcd 암호화, 외부 비밀 저장소
    이미지 버전 태그 지정 취약점 스캔, 이미지 서명

    운영 베스트 프랙티스 8¶

    YAML을 클러스터에 올리기 전에 확인합니다. 괄호는 배운 날입니다.

    보안 운영
    1 root로 돌리지 않는다: runAsNonRoot, allowPrivilegeEscalation false (5일차) 5 이미지는 버전 태그. latest 대신 정해진 태그 (1일차)
    2 네임스페이스에 PSA: warn으로 보고 restricted로 enforce (5일차) 6 설정과 비밀은 이미지 밖에: ConfigMap, Secret (4일차)
    3 앱마다 전용 SA, 최소 권한. API를 안 쓰면 토큰을 끈다 (5일차) 7 모든 앱에 probe와 자원: readiness, requests, limits (4일차)
    4 통신은 기본 차단. deny-all 후 필요한 길만, DNS 포함 (5일차) 8 남을 데이터는 PVC에. 백업은 따로, 한 파일에 쓰면 Recreate (4, 5일차)

    과정 전체 정리¶

    노트북을 원래대로 돌려놓고 싶을 때 아래 순서로 합니다. 계속 연습할 거라면 하지 않아도 됩니다.

    1. 5일차 네임스페이스 지우기. 이미 지운 것은 건너뜁니다.

    kubectl delete ns webapp broken secure rbac-lab np-lab --ignore-not-found

    2. Gateway 리소스 지우기. GatewayClass는 네임스페이스에 속하지 않아서 따로 지웁니다. 3일차의 eg도 남아 있으면 함께 지웁니다.

    kubectl delete gatewayclass blog-gw-class --ignore-not-found

    kubectl delete gateway eg --ignore-not-found

    kubectl delete gatewayclass eg --ignore-not-found

    3. Envoy Gateway 제거. 3일차에 설치할 때 쓴 install.yaml로 지웁니다. 버전은 3일차 실습 5에서 설치한 것과 같아야 합니다.

    kubectl delete -f https://github.com/envoyproxy/gateway/releases/download/v1.9.2/install.yaml --ignore-not-found

    envoy-gateway-system 네임스페이스와 Gateway API CRD가 함께 지워집니다. 1~2분 걸릴 수 있습니다. 3일차에 파일로 내려받아 설치했다면 kubectl delete -f install.yaml로 지워도 같습니다.

    4. 남은 것 확인. 앞 일차에서 default 네임스페이스에 만든 것이 남아 있는지 봅니다.

    kubectl get all,pvc,configmap,secret

    service/kubernetes와 configmap/kube-root-ca.crt는 쿠버네티스 기본 리소스이니 그대로 둡니다. 나머지는 kubectl delete 종류 이름으로 지웁니다. 한꺼번에 비우고 싶으면 Docker Desktop의 Kubernetes 설정에서 Reset cluster를 누릅니다. 클러스터 안의 모든 리소스가 지워집니다.

    5. 클러스터 끄기. Docker Desktop 왼쪽 메뉴 Kubernetes → Stop을 누릅니다. 버전에 따라 Settings → Kubernetes에서 Enable Kubernetes를 끄고 Apply를 누릅니다. 노트북 메모리를 돌려받습니다. 다시 쓸 때는 Kubernetes 켜기를 따라 켭니다.

    6. (선택) 이미지 지우기. 디스크 공간이 필요하면 실습 이미지를 지웁니다.

    docker rmi skilleat/frontend:v3-kb5 skilleat/backend:v3-kb5 skilleat/frontend:v4-kb5 skilleat/backend:v4-kb5 nginx:1.27 busybox:1.36

    사용 중이라 안 지워지는 이미지가 있으면 Docker Desktop을 다시 시작한 뒤 다시 실행합니다.
