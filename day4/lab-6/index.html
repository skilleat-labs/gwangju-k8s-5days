    실습 6. PVC로 데이터 지키기¶

    이번 실습에서 할 것

    • PVC를 만들고 PV가 자동으로 생기는 것(동적 프로비저닝)을 봅니다.
    • 실습 5와 같은 실험을 PVC로 다시 해서, Pod를 지워도 데이터가 남는 것을 봅니다.
    • Pod, PVC, 노드가 없어질 때 데이터가 어떻게 되는지, 데이터 보존과 서비스 연속성의 차이를 정리합니다.

    소요 시간 약 12분, 교안 DAY 4 섹션 6

    준비¶

    day4 폴더에서 합니다. 실습 5의 mysql Deployment와 mysql-secret(비밀번호 skilleat)이 남아 있는 상태에서 시작합니다.

    이번 실습에서 쓸 파일은 두 개입니다.

    1. PVC (저장 공간 요청서)

    mysql-pvc.yaml
    apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-pvc
spec:
  storageClassName: hostpath
  accessModes: [ReadWriteOnce]
  resources:
    requests: { storage: 1Gi }
    mysql-pvc.yaml 내려받기

    부분 뜻
    storageClassName: hostpath Docker Desktop의 기본 StorageClass. 빼도 기본값이 쓰입니다. STEP 30에서 이름을 확인합니다.
    accessModes: [ReadWriteOnce] 한 노드에서 읽기, 쓰기 (RWO).
    storage: 1Gi 필요한 용량.

    2. PVC를 쓰는 MySQL Deployment

    mysql-emptydir.yaml을 복사해 mysql-pvc-deploy.yaml로 저장하고 두 곳만 고칩니다. 아래 파일에서 바뀐 줄은 강조 표시했습니다.

    mysql-pvc-deploy.yaml
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: mysql
spec:
  strategy:
    type: Recreate
  selector: { matchLabels: { app: mysql } }
  template:
    metadata: { labels: { app: mysql } }
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        envFrom: [{ secretRef: { name: mysql-secret } }]
        readinessProbe:
          exec: { command: [mysqladmin, ping, -h, 127.0.0.1] }
        volumeMounts:
        - { name: data, mountPath: /var/lib/mysql }
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: mysql-pvc
    mysql-pvc-deploy.yaml 내려받기

    바뀐 곳 뜻
    strategy: type: Recreate 옛 Pod를 먼저 끄고 새 Pod를 띄웁니다. 롤링 업데이트는 새 Pod를 먼저 띄우는데, 두 MySQL이 한 데이터 폴더를 동시에 열면 안 됩니다.
    persistentVolumeClaim: claimName: mysql-pvc emptyDir 대신 PVC 이름을 적습니다. Pod는 PV를 모르고 PVC 이름만 압니다.

    Secret, mountPath 등 나머지는 실습 5와 같습니다.

    STEP 30. 기본 StorageClass 확인¶

    kubectl get storageclass


    NAME                 PROVISIONER          RECLAIMPOLICY   VOLUMEBINDINGMODE   ALLOWVOLUMEEXPANSION   AGE
hostpath (default)   docker.io/hostpath   Delete          Immediate           false                  3d
    출력은 예시입니다. 이름, IP, 시간은 사람마다 다릅니다.

    이름 옆에 (default)가 있는 것이 기본 StorageClass입니다.

    환경에 따라 다를 수 있음

    Docker Desktop 버전과 클러스터 방식에 따라 결과가 다를 수 있습니다.

    • 이름이 hostpath가 아니면: mysql-pvc.yaml의 storageClassName: 값을 그 이름으로 바꾸거나, storageClassName: 줄을 지웁니다. 줄을 지우면 (default) StorageClass가 쓰입니다.
    • VOLUMEBINDINGMODE가 WaitForFirstConsumer면: STEP 31에서 PVC가 Pending이고 PV가 아직 없는 것이 정상입니다. STEP 32에서 Pod가 PVC를 쓰는 순간 PV가 생기고 Bound가 됩니다.
    • No resources found로 StorageClass가 하나도 없으면: PVC가 계속 Pending입니다. 강사에게 알려 주세요.

    STEP 31. emptyDir MySQL 지우고 PVC 만들기¶

    실습 5의 emptyDir MySQL Deployment를 먼저 지웁니다. 같은 이름의 Deployment에 strategy만 바꿔 apply하면 오류가 나기 때문입니다 (아래 막히면 참고).

    kubectl delete deployment mysql

    PVC를 만듭니다.

    kubectl apply -f mysql-pvc.yaml

    deployment.apps "mysql" deleted
persistentvolumeclaim/mysql-pvc created

    PVC와 PV를 한 번에 봅니다.

    kubectl get pvc,pv


    NAME                              STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
persistentvolumeclaim/mysql-pvc   Bound    pvc-3f1e2d4c-5b6a-4c7d-8e9f-0a1b2c3d4e5f   1Gi        RWO            hostpath       5s

NAME                                                        CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM               STORAGECLASS   AGE
persistentvolume/pvc-3f1e2d4c-5b6a-4c7d-8e9f-0a1b2c3d4e5f   1Gi        RWO            Delete           Bound    default/mysql-pvc   hostpath       5s
    출력은 예시입니다. 이름, IP, 시간은 사람마다 다릅니다.

    우리가 만들지 않은 PV가 pvc-로 시작하는 이름으로 생겼고, PVC와 PV 모두 Bound입니다. PVC가 오자 StorageClass가 PV를 자동으로 만든 것, 즉 동적 프로비저닝입니다.

    STEP 32. PVC를 쓰는 MySQL 올리기¶

    kubectl apply -f mysql-pvc-deploy.yaml

    deployment.apps/mysql created

    READY가 1/1이 되면 Ctrl + C로 멈춥니다. 실습 5와 같은 readinessProbe가 있어 초기화가 끝나야 1/1이 됩니다.

    kubectl get pods -l app=mysql -w
# READY 확인 후 Ctrl+C


    NAME                     READY   STATUS              RESTARTS   AGE
mysql-7b9c6d5f4e-h3j5k   0/1     ContainerCreating   0          2s
mysql-7b9c6d5f4e-h3j5k   0/1     Running             0          10s
mysql-7b9c6d5f4e-h3j5k   1/1     Running             0          40s
    출력은 예시입니다. 이름, IP, 시간은 사람마다 다릅니다.

    STEP 33. 데이터 넣기 (실습 5와 같은 SQL)¶

    READY가 1/1이 된 뒤 접속합니다.

    kubectl exec -it deploy/mysql -- mysql -uroot -pskilleat

    mysql> 프롬프트에서 실습 5와 똑같이 입력합니다.

    CREATE DATABASE blog;
CREATE TABLE blog.post (id INT, title VARCHAR(50));
INSERT INTO blog.post VALUES (1, 'hello');
exit
    mysql> 프롬프트 없이 한 줄씩 실행하기

    먼저 Pod 이름을 확인해 복사합니다.

    kubectl get pods -l app=mysql

    <Pod 이름> 자리에 꺾쇠 없이 붙여 넣고 실행합니다.

    kubectl exec -it <Pod 이름> -- mysql -uroot -pskilleat -e "CREATE DATABASE blog;"

    kubectl exec -it <Pod 이름> -- mysql -uroot -pskilleat -e "CREATE TABLE blog.post (id INT, title VARCHAR(50));"

    kubectl exec -it <Pod 이름> -- mysql -uroot -pskilleat -e "INSERT INTO blog.post VALUES (1, 'hello');"

    STEP 34. Pod 지우고 READY 1/1 뒤 다시 확인¶

    실습 5처럼 Pod를 지웁니다.

    kubectl delete pod -l app=mysql

    새 Pod의 READY가 1/1이 될 때까지 봅니다. Pod 이름이 바뀐 것도 확인합니다. Ctrl + C로 멈춥니다.

    kubectl get pods -l app=mysql -w
# READY 확인 후 Ctrl+C

    다시 접속합니다.

    kubectl exec -it deploy/mysql -- mysql -uroot -pskilleat

    SELECT * FROM blog.post;

    +------+-------+
| id   | title |
+------+-------+
|    1 | hello |
+------+-------+
1 row in set (0.00 sec)

    exit로 나옵니다.

    mysql> 프롬프트 없이 확인하기

    kubectl get pods -l app=mysql로 새 Pod 이름을 복사해 넣습니다.

    kubectl exec -it <Pod 이름> -- mysql -uroot -pskilleat -e "SELECT * FROM blog.post;"

    Pod는 사라졌다 새로 생겼지만 PVC와 PV는 Pod 밖에 그대로 있었고, 새 Pod가 같은 PVC를 다시 붙였습니다. 실습 5와 같은 실험, 결과만 다릅니다.

    정리하기 전에: 무엇이 사라지면 데이터도 사라지나¶

    사라지는 것 데이터 이유
    Pod 남습니다 PVC, PV는 Pod 밖에 있고 새 Pod가 다시 붙입니다 (STEP 34).
    PVC reclaimPolicy가 정합니다 Delete(동적 프로비저닝 기본값)면 PV와 데이터도 지워집니다. Retain이면 PV와 데이터가 Released 상태로 남습니다.
    노드 저장소 종류가 정합니다 Docker Desktop의 hostpath는 그 노드 안의 폴더입니다. 노드를 잃으면 데이터도 잃고, 다른 노드에서 자동으로 쓰이지 않습니다. 클라우드 디스크, NFS 같은 네트워크 저장소는 다른 노드에 다시 붙일 수 있습니다.

    PVC는 백업이 아닙니다. 실수로 PVC를 지우거나 노드를 잃는 경우는 백업으로 대비합니다.

    사용 중인 PVC를 지우면

    Pod가 쓰고 있는 PVC를 지우면 바로 지워지지 않고 Terminating 상태로 기다립니다. 쓰는 Pod가 없어진 뒤에 지워집니다. 그래서 정리할 때 Deployment를 먼저 지웁니다.

    데이터 보존과 서비스 연속성은 다릅니다

    STEP 34의 성공은 데이터 보존입니다. 서비스가 끊기지 않았다는 뜻은 아닙니다. MySQL이 한 대이고 Recreate라서, Pod를 지운 순간부터 새 Pod가 READY 1/1이 될 때까지는 접속할 수 없습니다. 그동안의 요청은 실패합니다. 끊기지 않게 하려면 여러 대와 DB 복제 구성이 필요합니다 (StatefulSet이 복제를 자동으로 구성해 주지는 않습니다).

    성공하면¶

    • STEP 30: hostpath (default)가 보입니다.
    • STEP 31: PVC, PV 모두 STATUS Bound입니다.
    • STEP 34: 새 Pod에서도 1, hello가 남아 있습니다.

    막히면¶

    PVC가 Pending

    PVC의 Events를 봅니다.

    kubectl describe pvc mysql-pvc
    • storageclass.storage.k8s.io "hostpath" not found: storageClassName 오타이거나 이름이 다릅니다. STEP 30의 이름으로 고치고, PVC를 지운 뒤(kubectl delete pvc mysql-pvc) 다시 만듭니다.
    • waiting for first consumer to be created before binding: 바인딩 모드가 WaitForFirstConsumer입니다. 정상입니다. STEP 32으로 가면 Bound가 됩니다.
    The Deployment \"mysql\" is invalid: spec.strategy.rollingUpdate: Forbidden: may not be specified when strategy type is 'Recreate'

    실습 5의 mysql Deployment를 지우지 않고 mysql-pvc-deploy.yaml을 apply했습니다. 지우고 다시 올립니다.

    kubectl delete deployment mysql

    kubectl apply -f mysql-pvc-deploy.yaml
    Pod가 Pending, Events에 unbound immediate PersistentVolumeClaims

    PVC가 아직 Bound가 아닙니다. 위 PVC가 Pending을 봅니다.

    ERROR 2002 (HY000): Can't connect to local MySQL server through socket

    새 Pod가 아직 기동 중입니다. READY가 1/1이 된 뒤 다시 접속합니다.

    STEP 33에서 ERROR 1007 (HY000): Can't create database 'blog'; database exists

    이미 blog가 있습니다. STEP 33을 두 번 했거나, 앞에서 만든 데이터가 PVC에 남아 있는 것입니다. 그대로 STEP 34로 갑니다.

    ERROR 1045 (28000): Access denied for user 'root'@'localhost'

    비밀번호가 다릅니다. kubectl get secret mysql-secret -o go-template="{{.data.MYSQL_ROOT_PASSWORD | base64decode}}"로 값을 확인합니다. PVC에는 처음 초기화할 때의 비밀번호가 저장되어, 그 뒤 Secret을 바꿔도 root 비밀번호는 바뀌지 않습니다.

    정리¶

    오늘의 마지막 실습입니다. 아래 순서대로 지웁니다.

    kubectl delete deployment mysql

    kubectl delete pvc mysql-pvc

    kubectl delete secret mysql-secret

    kubectl delete configmap app-config

    PVC를 지우면 데이터도 지워집니다

    reclaimPolicy가 Delete면(STEP 30의 RECLAIMPOLICY 칸) PVC를 지울 때 PV와 그 안의 데이터도 함께 지워집니다. 실제 운영에서는 PVC를 지우기 전에 반드시 백업합니다.

    환경에 따라 다를 수 있음

    reclaimPolicy가 Retain이면 PVC를 지워도 PV가 Released 상태로 남습니다. kubectl get pv로 확인하고 남아 있으면 kubectl delete pv <PV 이름>으로 지웁니다.

    빠뜨린 것이 있으면 오늘의 실습의 하루를 마치고 한꺼번에 정리 명령을 실행합니다.
