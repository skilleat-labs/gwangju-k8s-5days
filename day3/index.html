    3일차 Service와 Gateway¶

    오늘이 끝나면 할 수 있는 것

    • Service로 변하지 않는 주소를 만들고, CoreDNS 덕분에 IP 대신 이름으로 접속합니다.
    • 밖에서 접속하는 방법(NodePort, LoadBalancer, port-forward)을 고르고, 연결이 안 될 때 EndpointSlice를 보고 원인을 찾습니다.
    • Envoy Gateway로 문 하나를 세우고, HTTPRoute로 /app1, /app2를 두 앱에 나눠 보냅니다.

    어제는 Deployment로 자가복구, 스케일링을 풀었고, Pod를 하나씩 바꾸는 순차 교체 원리를 확인했습니다. 실제 요청이 끊기지 않는지는 Service와 readiness를 붙인 뒤 확인합니다. 남은 한계는 "Pod가 바뀌면 주소도 바뀐다"입니다. 오늘은 하루 종일 이 주소 이야기를 합니다.

    실습 4 EndpointSlice와 연결 장애 4 EndpointSlice 10~15 약 14분 주소 목록 읽기, 늘어나는 주소 보기, 라벨 오타 장애 찾고 고치기

    "서비스에 접속이 안 돼요"라는 문의의 상당수는 EndpointSlice 하나만 보면 풀립니다. 실습 4의 디버깅 순서(Service → EndpointSlice → Pod → 라벨)는 4일차, 5일차에도 그대로 씁니다.

    터미널을 새로 열 때마다 이 폴더로 다시 이동합니다. 실습 3, 4, 6에서는 터미널을 두 개 씁니다.

    cd $HOME\k8s-labs\day3

    cd ~/k8s-labs/day3

    어제 web Deployment가 없으면¶

    오늘 실습은 어제 만든 web Deployment(nginx, Pod 3개, 라벨 app: web)를 그대로 씁니다. 먼저 남아 있는지 봅니다.

    kubectl get deploy web


    NAME   READY   UP-TO-DATE   AVAILABLE   AGE
web    3/3     3            3           1d
    출력은 예시입니다. 이름, IP, 시간은 사람마다 다릅니다.

    Error from server (NotFound): deployments.apps "web" not found가 나오면 아래 파일로 다시 만듭니다. 어제 이미지 버전을 바꿨거나 replicas가 3이 아니어도 아래 파일을 apply하면 오늘 실습과 같은 상태가 됩니다.

    web-deploy.yaml
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - containerPort: 80
    web-deploy.yaml 내려받기

    kubectl apply -f web-deploy.yaml

    kubectl get pods -l app=web


    NAME                   READY   STATUS    RESTARTS   AGE
web-7d9f8c6b5-abcde    1/1     Running   0          20s
web-7d9f8c6b5-fghij    1/1     Running   0          20s
web-7d9f8c6b5-klmno    1/1     Running   0          20s
    출력은 예시입니다. 이름, IP, 시간은 사람마다 다릅니다.

    세 줄 모두 1/1 Running이면 준비가 끝났습니다.

    오늘 끝나고 정리¶

    실습 6까지 끝났으면 아래를 정리합니다. 각 실습 페이지의 정리를 따라왔다면 대부분 이미 지워져 있습니다.

    Gateway eg는 오늘 꼭 지웁니다

    Gateway eg는 HTTP 80번 문을 씁니다. 남겨 두면 5일차 미니 블로그의 Gateway blog-gw(역시 80번)와 겹칩니다. 첫 번째 명령이 eg의 Gateway와 GatewayClass를 지웁니다. Envoy Gateway 설치는 지우지 않습니다.

    kubectl delete -f route.yaml -f app1.yaml -f app2.yaml -f gateway.yaml --ignore-not-found

    kubectl delete svc web-np web-lb --ignore-not-found

    kubectl delete namespace other --ignore-not-found

    kubectl scale deployment web --replicas=3

    지우지 마세요

    • Envoy Gateway 설치(envoy-gateway-system 네임스페이스와 Gateway API CRD)는 5일차 미니 블로그 종합 배포에서 그대로 씁니다. install.yaml로 delete하지 마세요.
    • web Deployment와 web Service도 남겨 둡니다 (강의 마지막 장 안내). 4일차 readinessProbe 실습은 web-probe라는 새 Deployment를 따로 만들므로 이름이나 라벨이 겹치지 않습니다.

    남은 것을 확인합니다.

    kubectl get deploy,svc

    kubectl get pods -n envoy-gateway-system


    NAME                             READY   STATUS    RESTARTS   AGE
envoy-gateway-6c7f5d9b8d-x2k7p   1/1     Running   0          1h
    출력은 예시입니다. 이름, IP, 시간은 사람마다 다릅니다.

    envoy-default-eg-로 시작하는 프록시 Pod는 gateway.yaml을 지우면 함께 사라집니다. 컨트롤러 envoy-gateway Pod 하나만 남으면 정상입니다. Gateway가 하나도 안 남았는지도 봅니다.

    kubectl get gateway -A

    No resources found가 나오면 됩니다.
